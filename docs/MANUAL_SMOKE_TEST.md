# 실제 Discord / CLI 수동 스모크 테스트

이 문서는 **미실행 체크리스트**입니다. Codex Cloud에서 수행한 Fake Discord/Interaction,
테스트용 PTY 및 구조화 fixture 검증은 실제 Discord gateway·Button·rate limit·CLI 인증의
E2E 검증을 대신하지 않습니다. 각 항목은 실제 사용 환경에서 실행하고 결과를 별도로 기록하세요.

## 준비

- 폐기 가능한 Linux 작업 디렉터리에서 진행하고 중요한 파일·운영 비밀을 두지 않습니다.
- Python 3.10 또는 3.12 가상환경에 `requirements-dev.txt`를 설치합니다.
- `.env.example`을 참고해 로컬 `.env`에 본인 Discord 봇 토큰과 소유자 ID를 설정합니다.
  토큰·`.env`·실제 터미널 출력·실제 감사 로그·nonce가 보이는 화면을 커밋하지 않습니다.
- Developer Portal에서 Message Content Intent를 활성화하고, `bot` 및
  `applications.commands` scope로 봇을 본인 서버에 초대합니다. 봇과 같은 서버에 참여하고
  DM을 허용합니다. 모든 원격 명령은 소유자와 봇의 **1:1 DM**에서 실행합니다.
- `agy`, `codex`, `claude`, `opencode` 중 사용할 CLI를 설치하고 로컬에서 인증합니다.
  기본 동시 세션 수는 최초 로컬 세션을 포함해 3개입니다. 네 CLI를 모두 점검할 때는
  추가 세션을 하나씩 종료하며 교체하세요. 각 CLI 버전은 별도로 기록합니다.
- 감사 경로의 최종 디렉터리는 `0700`, 파일은 `0600`이어야 합니다. 기본 위치는
  `$XDG_STATE_HOME/dishell/audit.jsonl` 또는 `~/.local/state/dishell/audit.jsonl`입니다.
- 모든 입력/관리는 작업별 확인 대상입니다. 미리보기에서 Enter/ESC 등 바이트와 대상 세션을
  확인하고, 파일 변경·셸 실행·CLI 내부 권한 우회를 요구하는 입력은 사용하지 않습니다.

## 순서와 예상 결과

### 1. Discord 봇 연결

기존 alias의 `agy` 또는 저장소 루트의 `.venv/bin/python main.py`로 시작합니다.
추가 진입점의 시작 연결도 별도로 확인하려면 다음을 사용합니다.

```bash
.venv/bin/python -m dishell --cli agy --remote
```

**예상:** 로컬 TUI가 TTY로 표시되고 키 입력/리사이즈가 동작합니다. `--remote` 사용 시
소유자 DM에 읽기 전용 연결 안내가 옵니다. 토큰·Intent·DM 설정이 잘못되면 로컬에 연결
실패를 표시하며 원격 입력을 활성화하지 않습니다. 중복 실행한 브릿지는 종료하고 다음 단계는
하나의 매니저에서 진행합니다.

### 2. 로컬 `/rc on`

`--remote` 없이 실행한 로컬 TUI에서 `/rc on`을 입력합니다. `/rc status`도 확인합니다.

**예상:** `/rc` 입력은 CLI에 전달되지 않고 아래 상태줄에 표시됩니다. 연결 후 전체 화면이
세션 ID와 블록 번호가 표시된 DM 메시지로 구성됩니다. 기본 권한은 VIEW이고 원격 연결 중
화면 너비가 설정값으로 좁아집니다. 이미 연결됐다면 추가 Discord 로그인을 만들지 않습니다.

### 3. `/sessions`

소유자 DM에서 `/sessions`와 실제 Slash Command `/sessions`를 각각 호출합니다.
가능한 경우 다른 테스트 계정의 DM 및 서버 채널 Slash Command로도 접근을 시도합니다.

**예상:** 소유자 DM에 최초 세션의 ID·도구·상태·활성 표시가 보입니다. 조회가 PTY 입력을
발생시키지 않습니다. 다른 사용자와 서버/그룹 DM 컨텍스트는 거부되며 세션 정보가 노출되지
않습니다. 명령 자동완성이 서버에 보여도 실행 권한이 생기지 않습니다.

### 4. `/session start codex`

소유자 DM에서 `/session start codex`를 보내고 확인 메시지의 세션 ID와 `MANAGE/start`를
확인합니다. 버튼 승인 전 `/sessions`에서 프로세스가 추가되지 않았는지 확인한 뒤 승인합니다.

**예상:** 승인 전 새 CLI를 실행하지 않습니다. 승인 후 고정된 ID의 Codex 세션 하나만
시작하며 기존 활성 세션은 유지됩니다. CLI 미설치이면 로컬 실행 파일 설정을 확인하라는
오류가 나오고 다른 실행 파일로 대체하지 않습니다. 경로/실행 옵션을 명령 뒤에 붙이면
거부합니다. 최대 세션 수를 넘으면 시작을 거부합니다.

### 5. `/session attach <id>`

새 Codex ID로 `/session attach <id>`를 보내고 확인 버튼을 승인합니다.
`/session status <id>`와 `/sessions`를 확인합니다.

**예상:** 승인 전에는 활성 세션이 바뀌지 않습니다. 승인 후 Codex의 전체 화면을 새 메시지
집합으로 구성하며 제목의 ID가 일치합니다. 로컬 터미널은 최초 AGY에 고정됩니다.
세션 전환 전에 발행한 미사용 입력 승인 버튼은 사용할 수 없습니다.

### 6. `/say` 입력 후 승인

활성 CLI에서 외부 도구를 실행하지 않는 짧은 인사 프롬프트를 사용합니다.
먼저 `/say` Slash Command로, 다음에는 일반 DM `/say ...`로 동일한 흐름을 확인합니다.
여러 줄 텍스트도 한 번 점검합니다.

**예상:** 확인 메시지에 고정된 대상 ID와 입력 바이트 미리보기가 표시되고 승인 전에는
CLI에 아무것도 쓰지 않습니다. 승인 후 한 번만 입력합니다. 여러 줄은 bracketed paste로
묶고 Enter 한 번으로 제출합니다. 동일 승인 버튼 재사용/동시 클릭은 추가 입력을 발생시키지
않습니다. 화면 또는 다른 입력 revision이 바뀌면 승인을 거부하므로 최신 화면에서 재요청합니다.
CLI 자체 승인 프롬프트는 자동으로 확정하지 않으며 `/key enter`도 별도 확인이 필요합니다.

### 7. 승인 거부

`/say` 또는 `/key enter` 요청을 만들고 **거부** 버튼을 누릅니다. 그 버튼을 다시 눌러봅니다.

**예상:** 요청을 폐기하고 PTY 또는 대기 입력 버퍼에 내용이 남지 않습니다. 재사용해도
입력하지 않습니다. 감사 로그에는 거부 결정만 기록하고 프롬프트/터미널 출력/nonce는
기록하지 않습니다. 다른 사용자 버튼 시도는 거부하되 소유자의 유효한 요청을 소모하지 않습니다.

### 8. 만료된 버튼 재사용

출력이 안정된 화면에서 요청을 만들고 기본 60초 TTL을 지난 후 승인 버튼을 눌러봅니다.

**예상:** 버튼이 비활성화되거나 만료/무효한 요청으로 거부됩니다. 입력은 0회입니다.
재사용할 수 없고 감사 로그에 만료 기록이 남습니다. 버튼 UI가 갱신되지 않았더라도
서버 측 만료 검사를 우회할 수 없어야 합니다.

### 9. 연결 끊기 및 재연결

요청을 미승인 상태로 둔 채 브릿지 호스트의 네트워크를 잠시 끊었다 복구합니다. 또는 로컬
`/rc off` 후 `/rc on`을 사용합니다. 이전 버튼을 누르고 새 요청도 한 번 만들어봅니다.

**예상:** 연결이 끊기면 이전 nonce와 PTY에 아직 쓰지 않은 원격 버퍼를 폐기합니다.
재연결 후 이전 버튼은 무효이고 새 전체 화면을 복구합니다. 새 요청은 새로운 확인을 거쳐
실행합니다. 실패한 이벤트 알림은 재시도하며 다음 상태 때문에 사라지지 않습니다.
확인 UI 전송 실패/취소로 요청이 남아 실행 가능한 상태가 되어서는 안 됩니다.

### 10. 여러 CLI 세션 간 입력 분리

AGY와 Codex 두 세션을 각각 attach하고 서로 다른 무해한 표시용 프롬프트를 승인합니다.
추가 세션을 교체해 Claude와 OpenCode도 같은 절차를 수행합니다.

**예상:** 일반 입력은 요청할 때 고정한 세션으로만 전달하고 다른 세션에는 나타나지 않습니다.
A 세션의 승인으로 B를 조작할 수 없습니다. 각 화면·알림에 정확한 세션 ID가 표시됩니다.
단일 봇 연결을 공유하고 로컬 stdin은 최초 세션에 유지됩니다. 동시 입력은 피하고,
입력 사이에 화면이 바뀌면 요청을 다시 만듭니다.

### 11. 실제 TUI와 화면 동기화

로컬에서 몇 행의 한국어·Unicode 출력을 만들고 한 행만 변경해 봅니다. 터미널 크기를
바꾸고 여러 행을 스크롤한 뒤 `/session history <id> 0`도 확인합니다.
`/session status <id>`의 동기화 지표와 DM 메시지의 편집 여부를 비교합니다.

**예상:** 정지 화면은 edit가 증가하지 않고 한 행 변경은 해당 블록만 edit합니다.
스크롤·리사이즈·재연결 후 보이는 전체 화면이 실제 TUI와 일치하고 오래된 프레임이 새 화면을
덮어쓰지 않습니다. 스크롤 기록은 해당 세션으로만 조회합니다. 메시지 삭제/전송 오류 뒤에도
전체 화면을 복구해야 합니다. 원격 최대 240×60, 최대 16블록과 결합 문자 생략·색상 미지원
제약을 감안합니다. 실제 API rate limit의 재시도 지연은 로컬 합성 benchmark에서 검증하지
않았으므로 운영 환경에서 별도로 관찰합니다.

AGY 승인/idle fixture와 구조화 이벤트 출처는 `tests/fixtures/events/README.md`를 참고합니다.
Codex/Claude/OpenCode의 검증되지 않은 일반 TUI 문구는 UNKNOWN이 정상입니다.
OpenCode 서버 이벤트 어댑터에 자동 수집기는 없으므로 기본 PTY 모드에서 서버 상태 이벤트
E2E 성공을 기대하지 않습니다. 출력이 조용하다는 이유로 COMPLETED가 발생해서는 안 됩니다.

### 12. 감사 로그 및 세션 종료 확인

본인 환경에서 감사 로그의 **필드·파일 권한·사건 종류**만 확인합니다.
추가 세션을 `/session stop <id>`로 요청하고 승인합니다. 종료된 ID에 다시 입력을 시도하고,
최초 로컬 CLI를 끝내 매니저 종료까지 확인합니다. 별도의 폐기 가능한 감사 경로를 사용하는
테스트 실행에서만 경로를 쓰기 불가로 만들어 원격 요청의 fail-closed 동작도 점검합니다.

**예상:** 승인·거부·만료·권한 거부·시작/종료·입력 시도/결과가 UTC JSONL 메타데이터로
남습니다. 전체 입력·터미널 출력·비밀값·nonce가 없어야 합니다. 디렉터리/파일은 0700/0600이고
1 MiB/하루 회전, 최대 5개 보관 파일/7일 정리는 다음 감사 기록 시 수행합니다.
로그 실패 시 원격 작업을 거부합니다. 결과 기록에 실패하면 추가 원격 작업도 차단합니다.
세션 종료 전에는 확인이 필요하고 종료 후에는 입력을 거부합니다. 최초 CLI 종료 시 추가 세션을
정리하고 PTY fd·프로세스 그룹을 회수하며 로컬 터미널 모드를 복구합니다.

**한계:** 이미 PTY에 쓰인 바이트는 되돌릴 수 없습니다. 확인 UI는 OS 샌드박스가 아니며
승인한 CLI 동작은 호스트 사용자의 권한으로 실행됩니다. 원격 화면에는 민감한 출력이 보이고
Discord 기록에 남을 수 있습니다. 처리 확인된 알림의 재전달 방지는 최근 1,024개 키의 LRU
범위에 한정됩니다. HTTP 전송 결과가 불명확한 실패에서는 재시도로 중복 알림이 도착할 수
있으므로 세션 ID·전이 번호를 함께 확인합니다.

## 결과 기록

위 1–12 항목에 대해 실행일·Python/CLI/Discord 버전·성공/실패·재현 절차를 기록합니다.
미실행 항목은 `미검증`으로 남깁니다. 문제가 있으면 토큰/프롬프트/로그 원문 대신
마스킹한 동작 설명과 오류 유형만 공유합니다. 이 문서 자체에는 실제 테스트 결과나 비밀값을
덧붙이지 않았습니다.
